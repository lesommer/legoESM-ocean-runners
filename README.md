# legoESM-ocean-runners

Experiment templates, runners, and reproducibility tools for ocean simulations with [legoESM](https://github.com/climate-federation/legoESM).

## What is this?

legoESM is a differentiable Earth-system model in JAX, developed upstream at
[climate-federation/legoESM](https://github.com/climate-federation/legoESM).
This repo makes it practical to run *ocean experiments* with it: a library of
ready-to-use experiment templates, a runner that adapts each run to your
machine (laptop, SLURM or OAR cluster), and a provenance record that lets you
re-run exactly the same experiment months later. You pick a template, override
the few parameters you care about, and the runner fetches any required data
and writes a small `experiment.tag` file recording what was run and against
which model version. The model itself is pinned to an exact commit, so results
do not drift as the model evolves. Three things you can do:

- **Run** — a curated ocean experiment from a template (idealized cases need
  no data; realistic OMIP lanes fetch theirs)
- **Adapt** — change any parameter with `-o key=value` overrides
- **Reproduce** — reconstruct the exact environment of any past run

A 30-second tour (after the [installation](#installation) below):

```bash
python scripts/init_experiment.py ocean/baroclinic_gyre \
    --name my_gyre --output-dir ./my_gyre -o time.duration_days=1
cd my_gyre && bash run.sh
```

Unfamiliar terms (pin, patch, recipe, runner tag, graduated template, ...) are
defined in the [Glossary](#glossary); the architecture rationale lives in
[Design notes](#design-notes-why-this-repo-exists).

## Installation

Prerequisites: Python ≥ 3.11 and [uv](https://docs.astral.sh/uv/) (or plain
pip), git. No GPU required — CPU JAX runs the idealized cases.

```bash
# 1. Clone this repo and legoESM side-by-side (the generated run.sh
#    resolves legoESM at ../legoESM)
git clone https://github.com/lesommer/legoESM-ocean-runners.git
git clone https://github.com/climate-federation/legoESM.git

# 2. Pin legoESM to the commit this repo is validated against
cd legoESM
git checkout $(grep '^commit:' ../legoESM-ocean-runners/legoESM_version.txt | cut -d: -f2 | tr -d ' ')

# 3. Install legoESM (uv workspace — plain pip cannot resolve the
#    federation package layout)
uv sync

# 4. Apply this repo's patches to the legoESM checkout (003-005 enable the
#    tripolar-OMIP MPI lane, runoff-file overrides and a barotropic tuning
#    knob; 006 stamps this repo's identity into the model's run manifest.
#    Patches are dropped automatically at pin bumps once merged upstream.)
cd ../legoESM-ocean-runners && bash scripts/apply_patches.sh

# 5. Verify
cd ../legoESM && python -c "import legoesm; print('legoESM OK')"
```

Note: `run.sh` invokes plain `python`, so have the legoESM environment
active when running experiments (`source ../legoESM/.venv/bin/activate`).
`python scripts/reproduce.py <experiment.tag>` performs the whole
checkout-and-patch sequence automatically for reproducing a past run.

To set up a complete experiment workspace — machine configs, a personal
experiment ledger, multi-machine workflows — see the
[experiment-ledger template](https://github.com/lesommer/legoESM-ocean-experiments-template)
and its setup guide.

## Run an experiment

### DINO (idealized, no data needed)

```bash
# 1. Initialize (paper-faithful R1 by default; see docs/dino.md for the
#    resolution ladder, multi-GPU, restart and ensemble lanes)
python scripts/init_experiment.py 3d_idealized/dino \
    --name my_dino --output-dir ./my_dino

# 2. Run
cd my_dino && bash run.sh
```

### Idealized (no data needed)

**Graduated templates** live in the pinned legoESM template library (`config/templates/ocean/<stem>.yaml`) and resolve by canonical name `ocean/<stem>` — pre-graduation names still resolve as legacy aliases. Graduated 2026-10-22: `baroclinic_gyre`, `acc_channel`, `eady_instability`, `geostrophic_adjustment`, `lock_exchange`, `overflow`, `phillips_two_layer`, `global_overturning`, `barotropic_wave`; also usable directly: `eady_uniform`, `held_larichev`, `munk_gyre`, `global_barotropic_wind`. The upstream lane's validated defaults apply (dt/duration/resolution); overrides are the curated layer.

```bash
# 1. Check data availability (idealized experiments need no data)
python scripts/fetch_data.py check ocean/baroclinic_gyre

# 2. Initialize (--output-dir is required). The upstream lane's validated
#    defaults apply (36x72, dt 300, 60 d); tip: for a first quick look,
#    shorten with -o time.duration_days=1. The pre-graduation workhorse
#    values come back as overrides:
python scripts/init_experiment.py ocean/baroclinic_gyre \
    --name my_gyre --output-dir ./my_gyre \
    -o time.duration_days=1

# 3. Run (upstream ocean test matrix executes the validated case config;
#    --only baroclinic_gyre also runs its _cos variant — two cases)
cd my_gyre && bash run.sh
```

### Global ocean / OMIP (requires data)

```bash
# 1. Fetch required data
python scripts/fetch_data.py fetch global_ocean/omip_tripole

# 2. Initialize
python scripts/init_experiment.py global_ocean/omip_tripole \
    --name orca1_phase0 --output-dir ./orca1_phase0

# 3. Run (or submit run.sh to your scheduler)
cd orca1_phase0 && bash run.sh
```

## Modify an experiment

Templates are the starting point. Override any parameter with dot-notation `-o` flags:

```bash
# Higher resolution and longer run (graduated template: overrides are the
# only curated layer — the upstream lane owns dt/duration/resolution)
python scripts/init_experiment.py ocean/baroclinic_gyre \
    --name gyre_hires --output-dir ./gyre_hires \
    -o grid.resolution=128x256 \
    -o time.duration_days=730

# Change vertical mixing scheme
python scripts/init_experiment.py global_ocean/omip_jra55 \
    --name omip_kpp --output-dir ./omip_kpp \
    -o physics.vertical_mixing.scheme=kpp
```

## Reproduce an experiment

Every run produces an `experiment.tag` (INI format) recording the full software environment, and every run-time `run_manifest.json` (written by legoESM) additionally carries the runners-layer identity (`[reproducibility] runner_tag` / `patches`, stamped via `LEGOESM_RUNNER_TAG` / `LEGOESM_RUNNER_PATCHES` from the generated `run.sh` — the manifest is the run-time superset of the tag):

```ini
[legoESM]
ref = main
commit = 1f6a1df4cf36b78a6ab4f5602ba5e75795e78dae
patches = 003-omip-core2-mpi.patch,004-runoff-file-override.patch,...
patch_sha256_004-runoff-file-override = sha256:d2e738b0ece1ccca

[reproducibility]
runner_tag = legoesm-1f6a1df4cf36-20261022b
overrides = ["grid.resolution=128x256", "time.duration_days=730"]
python_version = 3.12.12
jax_version = 0.10.0
```

To reproduce:

```bash
python scripts/reproduce.py path/to/experiment.tag          # reconstruct the environment
python scripts/reproduce.py path/to/experiment.tag --verify # audit the tag against the current checkout
python scripts/reproduce.py path/to/experiment.tag --run    # ... and re-init (re-applying the recorded overrides)
```

This checks out the runner tag → checks out the legoESM commit → applies patches → verifies data. `--verify` recomputes the config hash from template + recorded overrides and checks every recorded patch content digest (exit 1 on drift); `--run` re-applies the recorded overrides so the rerun is the same experiment, not a template-default lookalike.

## Glossary

| Term | Meaning |
|------|---------|
| **template** | A YAML file declaring an experiment: the case, grid, duration, and data it needs. Lives in [`templates/`](templates/) here, or in legoESM's own template library once graduated. |
| **graduated template** | A template whose case is now maintained in legoESM's template library; it resolves by the canonical upstream name `ocean/<stem>`. This repo keeps only curated overrides for it. |
| **legacy alias** | A pre-graduation template name (e.g. `3d_idealized/baroclinic_gyre`) that still resolves to its graduated template, so old experiments keep working. |
| **override** | A `-o key=value` parameter change applied at init (dot-notation, e.g. `-o time.duration_days=730`); recorded in the tag. |
| **pin** | `legoESM_version.txt` records the exact model commit this repo is validated against; a "pin bump" moves it to a newer commit after validation. |
| **patch** | A small change to the model carried in `patches/` until it is merged upstream; patches are re-verified at every pin bump and dropped once merged. |
| **`experiment.tag`** | The init-time provenance file written next to your config: model commit, patches (with SHA-256 digests), overrides, machine, runner tag. |
| **`run_manifest.json`** | The model's own run-time record (written by legoESM at run start); it also carries the runners-layer identity (`runner_tag`, `patches`). |
| **runner tag** | A `legoesm-<hash>-<date>` git tag in this repo marking a validated compatibility point; every `experiment.tag` records the one it was created at. |
| **recipe** | The named scheme identity of an ocean configuration — which EOS, advection, pressure-gradient and time-integrator schemes it uses (see Design notes). |
| **card** | A named preset for a lane — e.g. the DINO recipe cards (`nemo_dino_kamm`, ...) select a scientifically validated configuration. |
| **lane** | A dispatch path in the runner for a family of cases (e.g. the matrix-delegated idealized lanes, the tripole OMIP lane). |
| **receipt** | A recorded run-test result for a template (machine, date, outcome), kept in [project_status.md](project_status.md). |

## Design notes: why this repo exists

legoESM is a model repository — and it now ships its own reproducibility
spine: versioned experiment templates under `config/templates/`, init
ergonomics (`scripts/experiment/init_experiment.py`), a `legoesm run`
entry point, a per-run `run_manifest.json` (resolved configuration,
config hash, final state digest) written at run start, and `legoesm
reproduce --check` to re-run a manifest and bit-check the result. The
manifest is designed upstream as a **superset of this repo's
`experiment.tag`** — same section names, plus `runner_tag`/`patches`
fields that exist precisely for this repo to stamp itself into — and
upstream asks downstreams not to build parallel provenance systems.
This repo does not duplicate that spine.

That spine executes and re-verifies a single run. A typical user,
however, wants to run *experiments*: a series of configured runs, across
several machines, revisited over months. Between the model and that
workflow there is a gap:

- **Named configurations.** Upstream's `--config` lane is deliberately
  narrow (only `ocean.*` fields, only some lanes; grid/mesh/run controls
  stay CLI flags), and its template library is generic. There is no way
  to say "the NEMO-faithful card, at this resolution, for 2 years" once
  and then vary one parameter at a time.

- **Reproducibility across environments.** The manifest describes one
  run, but it cannot reconstruct an environment that involved features
  not yet merged into legoESM, and it carries no notion of *which*
  configuration template a run came from.

- **Data.** Realistic runs need grids, bathymetry, forcing and initial
  conditions. Upstream accepts a path to already-staged data; where the
  files come from, how they are verified, and how they are shared between
  machines is not upstream's concern.

- **Machines.** Clusters differ in schedulers, accounts, storage paths and
  GPU setup. Nothing upstream adapts a configuration to where it runs.

This repo fills that gap as a **thin delta layer over legoESM's spine** —
it owns what upstream does not (and should not) carry:

- **A curated ocean experiment set** — templates that declare their
  scheme identity by naming legoESM **recipes** from the pinned catalog
  (see *Recipes* below): the NEMO-faithful card, DINO recipe lanes, the
  tripole OMIP lanes, Neverworld2-lite, the SCM set, and the idealized
  matrix lanes. Generic templates graduate upstream as they stabilize
  (merge-and-remove, like patches); the curated/personal ones stay here.

- **The patch chain** — `legoESM_version.txt` pins the model commit,
  validated `legoesm-<hash>-<date>` tags mark compatibility points, and
  `patches/` holds pre-merge features. A run manifest *records* which
  patches were applied; only this repo can *reconstruct* the patched
  environment: `scripts/reproduce.py` walks runner tag → legoESM commit
  → patches → data check. Upstream's manifest verifies a rerun's
  digest; this chain reconstructs the run.

- **A data catalog** — `data_catalog.yaml` is the single source of truth
  for external files (URLs, checksums, sizes, access levels, citations),
  and `scripts/fetch_data.py` checks, fetches and verifies them per
  machine before a run starts.

- **Fleet operations** — templates are machine-agnostic; machine
  configuration (scheduler, accounts, paths, environment) is passed at
  init via `--machine` and the generated `run.sh` matches the machine's
  scheduler: SLURM machines get `#SBATCH` directives (submit with
  `sbatch run.sh`); OAR machines (GRICAD/CIMENT: bigfoot, dahu, kraken)
  get `#OAR` directives (submit with `oarsub -S ./run.sh` — the path
  form is required). Per-template run-tested receipts live in
  `project_status.md`, and CI blocks pushes to `main` when
  reproducibility-affecting files change without a tag.

- **Validation** — `scripts/validate_templates.py` checks templates
  against the pinned legoESM, including `ocean.recipe` declarations
  (below).

### Recipes (scheme identity)

In legoESM lingo, a **recipe** is the named *scheme identity* of an
ocean configuration — which EOS, advection, pressure-gradient,
barotropic solver and time integrators it uses — decoupled from the
**setup** (grid, initial conditions, forcing, resolution-dependent
parameters). A run is a (recipe, setup) pair. Recipes live in legoESM's
catalog (`legoesm.ocean.recipes`); every upstream test-matrix case is
tagged with the recipe it actually runs (`recipe_map.EXPERIMENT_RECIPES`),
and those tags are verified upstream by tests, so they cannot drift.

Templates in this repo declare their scheme identity with
`ocean.recipe`:

| Lane | `ocean.recipe` semantics |
|------|---------------------------|
| matrix lanes (`2d/`, `3d_idealized/`, `global_ocean/bench`, ...) | **required**; must equal the pinned recipe_map tag of `ocean.case` — the upstream case owns the recipe, the template declares it |
| `dino` | optional; names an upstream DINO recipe *card* (`run_dino.py --recipe`: `nemo_dino_kamm`, `nemo_dino_kamm_mlf`, `veros`, ...); unset = paper-faithful DINOConfig defaults |
| tripole OMIP (`omip_tripole`, `omip_core2_thin`) | the lane's fixed identity `omip_nemo_match_tripole_v1`; `omip_faithful_card` overrides dycore fields via `run.extra_args` and declares **nothing** (recipe names are fidelity claims — never declare an unverified identity) |
| `ocean_scm`, `coupled` | no ocean dycore recipe applies |

`scripts/validate_templates.py` resolves every declaration against the
*pinned* legoESM catalogs, so an upstream recipe rename or re-tagging
(`nemo_v1` → `legoesm_nemo_like_v1` happened, 2026-09-02) breaks
validation at pin-bump time, not at run time. The declaration is
recorded in `experiment.tag` (`[model] recipe = ...`).

### Position in the three-repo layout

```
legoESM (model, consumed read-only at a pinned commit)
   ^
   |  pinned commit (legoESM_version.txt)
this repo (templates, runners, patches, data catalog)
   ^
   |  template + overrides
my-legoESM-ocean-experiments (personal ledger: run declarations, machine
configs, notes, analysis) — see link below
```

Use this repo to declare and execute reproducible experiment
configurations; use a personal experiment ledger to record what you ran,
where, and what came of it. To start your own ledger,
use the [experiment-ledger template repository](https://github.com/lesommer/legoESM-ocean-experiments-template)
("Use this template" → private clone), which carries the run-declaration
format, machine-config template, and the bin/ helpers.
